## Mission réconciliation Stripe — point 4, MRR de repli invoice-only (2026-08-20)

- 2026-08-20 — Confirmé avant d'écrire le moindre code : l'exemption "un compte invoice-only ne doit jamais être court-circuité `isChurned`" que ce point demandait d'ajouter **existait déjà**, depuis D-NEXT (2026-08-04, voir CLAUDE.md). `calculate-scores/index.ts::scoreAccountPure` calcule `isChurned = isAccountChurned(subscriptions.map(s => s.status))`, et `isAccountChurned` (`_shared/mrr-engine.ts`) retourne `false` par construction quand `subscriptions.length === 0` — un compte invoice-only n'a jamais de ligne `subscriptions`, donc ne peut structurellement jamais être `isChurned`. Aucun changement nécessaire sur ce point ; seul le MRR de repli lui-même (`estimateInvoiceOnlyMrr`) était réellement manquant.
- 2026-08-20 — Le MRR de repli n'est câblé que dans `sync-stripe` (chemin batch, cron quotidien). `stripe-webhook` ne recalcule pas l'estimation en temps réel sur un event `invoice.paid` pour un compte invoice-only — recalculer une cadence à partir de l'historique complet à chaque event webhook aurait ajouté une requête DB (fetch de tout l'historique de factures payées) sur un chemin déjà temps-réel, pour un cas qui se corrige de toute façon au prochain `sync-stripe-all-orgs` (quotidien). Même arbitrage déjà fait pour `movement_date`/`provenance` (Lot 4, 2026-08-13 : "chemin batch seulement, webhook hors périmètre"). Un compte invoice-only qui reçoit un paiement via webhook affichera donc son MRR de repli à jour au plus tard le lendemain, pas immédiatement — acceptable pour une estimation, pas pour un montant confirmé.
- 2026-08-20 — Le MRR de repli n'alimente ni `mrr_movements` ni le calcul NRR/churn rate (`calcNrrPercentage`/`calcChurnRate30d`) — délibérément non wiré, une facture payée isolée ne permet pas de classer un mouvement `new`/`expansion`/`contraction` de façon fiable (pas de `Subscription.created` à dater). Un compte invoice-only avec MRR de repli reste donc invisible dans les vues MRR trend/NRR — cohérent avec `revenue_dynamics_score` qui restera `status='unavailable'` pour lui (aucun mouvement à mesurer), jamais une tendance fabriquée. Décision produit distincte à prendre si la couverture NRR doit un jour inclure ces comptes.
- 2026-08-20 (correctif post-revue Naima, avant merge) — **`estimateInvoiceOnlyMrr` (design initial "écart entre les 2 factures payées les plus récentes") s'est révélé faux contre la donnée réelle du golden fixture lui-même** (App'Ines, `cus_Rn6M1Tvnr0tOxS`) : un paiement manqué/en retard élargit l'écart entre les deux factures payées les plus récentes à 90 jours (2026-04-14 → 2026-07-13) sur un compte par ailleurs mensuel — l'ancien design calculait `mrr_cents=10132` (~101€), une sous-estimation ~3x du vrai ~299€/mois. Trouvé en vérifiant les vrais chiffres en base avant de répondre à la demande de Naima ("je veux voir les chiffres avant de juger si merger"), pas par une revue de code. Corrigé : la cadence est désormais la **médiane de tous les écarts consécutifs** entre factures payées (pas seulement les 2 dernières) — robuste à un seul écart irrégulier tant que la majorité de l'historique reste régulière. Sur les 15 factures payées réelles d'App'Ines (2025-02-18 → 2026-07-13), la médiane des 14 écarts vaut 32.5 jours → `mrr_cents≈28002` (≈280.02€/mois), un résultat matériellement correct (vs. le vrai ~299€/mois, l'écart restant venant de la variance naturelle des délais de paiement, pas d'un bug) au lieu d'un résultat faux d'un facteur 3. Vérification mutation-test faite : les deux tests de régression échouent bien contre l'ancien code (confirmé, `mrr_cents=10001` observé sur le scénario réduit) avant d'être validés contre le correctif.
- 2026-08-20 — **Découverte tangentielle en vérifiant les vrais chiffres App'Ines : la devise réelle de ce compte est EUR, pas USD.** Les 15 factures payées portent `currency='eur'`, montant `29900` = 299,00 €. Le rapport de fin de session précédent (avant ce correctif) avait présenté ce cas comme "$299/mois" sans jamais vérifier la devise réelle en base — une supposition, pas une vérification. `estimateInvoiceOnlyMrr` propage déjà `currency` correctement depuis l'input (`mostRecent.currency`), donc le code n'a pas ce bug ; seule la communication verbale précédente avait la devise fausse.

## Bug trouvé en vérifiant Point 2 : la branche "churned" d'`aggregateAccountMrr` est structurellement inatteignable depuis `sync-stripe` (2026-08-20)

- 2026-08-20 — **Bug pré-existant significatif, non introduit par la mission réconciliation, trouvé en répondant à la question de Naima sur Guillaume Odriosolo (`cus_RsEoDTmJXwysBd`)**. `aggregateAccountMrr` (`_shared/mrr-engine.ts`, depuis le 2026-08-04) a une branche dédiée : si `subs.length > 0` ET que toutes les subscriptions sont `canceled`, elle retourne `mrr_status='ok'`/`mrr_cents=0` (un $0 confirmé, affiché normalement, jamais "Not billable"). Mais `sync-stripe/index.ts` (lignes ~468-493) ne pousse dans `accountSubMeta` — le tableau passé à `aggregateAccountMrr` — QUE les subscriptions `active`/`trialing`/`past_due`/`unpaid` ; une subscription `canceled` n'y entre jamais. Résultat : un compte dont **toutes** les subscriptions sont `canceled` arrive toujours à `aggregateAccountMrr` avec un tableau **vide**, jamais avec un tableau non-vide "tout canceled" — la branche `churned` (lignes 342-354) est donc **inatteignable depuis ce call site**, quelle que soit la fraîcheur du sync. Le compte tombe dans la branche `subs.length===0`, `mrr_status='unavailable'`/`mrr_unavailable_reason='no_subscription_data'` — indiscernable d'un compte jamais synchronisé.
- 2026-08-20 — **Confirmé systémique, pas isolé à Guillaume** : requête directe sur le portefeuille dev (comptes avec ≥1 subscription connue, toutes `canceled`) — tous montrent `mrr_status='unavailable'`, sur des runs de sync étalés de 2026-03-14 à aujourd'hui (2026-08-20 14:04:56, le compte `da9c1afd-58a4-4b42-b2a5-e62707fc25f9` — celui de Guillaume dans l'org "jimogep851" — a été **créé** à cet instant précis par le sync du jour, donc ce n'est pas un vestige d'ancien code : c'est le comportement actuel). `calculate-scores` (chemin indépendant, `isAccountChurned`) classe correctement ce même compte `churn_risk_band='churned'` — la divergence est spécifiquement entre les deux écritures `accounts.mrr_status` (sync-stripe) et `accounts.churn_risk_band` (calculate-scores), qui ne se recoupent jamais.
- 2026-08-20 — **Conséquence directe pour Point 2** : le commentaire de `en.ts::mrrUnavailableReason` (ligne ~1923) affirme explicitement "un compte churné à $0 confirmé n'atteint jamais cette fonction (`mrr_status` reste `'ok'` pour lui)" — cette hypothèse est fausse pour tout compte dans ce cas (subscription unique canceled, ou toutes canceled). Pour le compte de Guillaume dans "jimogep851" : `billing_model` reste `'subscription'` (il a bien une vraie subscription, jamais classé `invoice_only`), donc une fois resynchronisé avec le code post-#93, il affichera **"Not billable — no billing data yet"** — un message trompeur pour un client qui a 9 factures et une souscription complète, mais qui est parti. Ce n'est pas une approximation du vrai motif, c'est le mauvais motif.
- 2026-08-20 — Non corrigé dans cette session : nécessite de décider comment `sync-stripe` doit traiter un compte 100%-canceled sans casser `accountLatestCanceledAt`/`newMrrByAccount`/la détection `movement_type='churn'` qui dépendent aussi de cette boucle de filtrage — un changement sur du code de scoring/data partagé par de nombreux comptes, hors du périmètre exact des 4 points de cette mission, à traiter comme son propre chantier (EXPLORE→PLAN→CODE, règle CLAUDE.md).

## Investigation clé Stripe partagée entre orgs de test (2026-08-20)

- 2026-08-20 — Il existe **4 chemins distincts** qui écrivent une connexion Stripe côté org, pas 2 comme le mandat initial le supposait : `verify-stripe-token` (onboarding réel `/onboarding/stripe`, `useOnboardingWizard.ts`), `update-stripe-connection` (Settings.tsx, `useStripeConnection.ts`), `stripe-oauth-callback` (OAuth, `stripe-oauth-initiate`), et `integration-oauth/stripe/api-key` (page Integrations.tsx, `useConnectStripeApiKey`). Aucun ne référence les autres — même classe de duplication que celle déjà signalée par l'audit branches 2026-08-06 (CLAUDE.md, règle 0), mais découverte ici en cherchant la garde d'unicité, pas en amont d'un chantier. À trancher séparément : lesquels de ces 4 chemins sont censés rester vivants.
- 2026-08-20 — `integration-oauth/index.ts` (`POST /stripe/api-key`, lignes ~345-349) écrit `organizations.stripe_account_id` sans jamais vérifier l'erreur retournée par l'UPDATE (`await supabase.from('organizations').update(...)` — `error` non déstructuré, non testé). Une collision sur la contrainte UNIQUE `organizations_stripe_account_id_key` échoue donc **silencieusement** : la fonction répond `success: true` alors que `stripe_account_id` n'a pas été écrit pour cette org. Pas de 500, pas de 409, aucune trace. Pré-existant, non corrigé ici (hors scope de la mission clé partagée — ce chemin permettait déjà involontairement le partage, juste avec un angle mort d'observabilité).
- 2026-08-20 — Plus significatif : ni `integration-oauth/stripe/api-key` ni `stripe-oauth-callback` n'écrivent jamais `organizations.stripe_api_key` — seulement `stripe_account_id`/Vault/`organization_integrations`. Or `sync-stripe/index.ts:1061` (`orgsToSync[0].stripe_api_key`) est la **seule** colonne lue pour synchroniser un org (confirmé par le commentaire déjà présent dans `update-stripe-connection/index.ts:24-30`, écrit lors d'un incident antérieur similaire sur `verify-stripe-token`). Une org connectée exclusivement via l'un de ces deux chemins ne synchronisera donc **jamais**, indépendamment de tout partage de clé — bug pré-existant, distinct de cette mission, non corrigé ici. Conséquence directe pour la preuve Phase 3 de la mission clé partagée : seuls `verify-stripe-token` et `update-stripe-connection` ont été utilisés pour la démonstration, les deux seuls chemins qui peuplent réellement `stripe_api_key`.
- 2026-08-20 — Fan-out webhook multi-org : évaluation initiale ("chantier non trivial", documenté comme limitation connue plutôt que corrigé) **révisée et corrigée le même jour** — chiffré plus précisément à la session suivante : la logique de traitement par event (`handleCustomerCreated`/`handleSubscriptionEvent`/`handleInvoiceEvent`/etc.) était déjà entièrement paramétrée par un seul `organizationId`, donc déjà tenant-safe pour être rejouée N fois. Le vrai obstacle était ailleurs — l'idempotence (`data_syncs.webhook_event_id`) n'était pas scopée par org (`.maybeSingle()` sur un futur >1 ligne aurait cassé le retry). Implémenté : `resolveOrganizationIds` retourne toutes les orgs correspondantes, boucle per-org avec idempotence scopée `organization_id`, isolation d'échec (le catch par-org ne `return` jamais — une org en échec n'empêche pas le traitement des autres). Aucun changement de schéma, aucune nouvelle queue. Voir commit sur `feat/allow-shared-stripe-key-testing`.
- 2026-08-20 (vérification post-merge, une fois en prod) — **Bug réel trouvé en écrivant un vrai test comportemental** de l'isolation per-org (au lieu du test par inspection du source du point ci-dessus, qui ne pouvait pas le voir) : le catch par-org lui-même ne contenait bien aucun `return`, mais l'idempotence (`data_syncs.select().maybeSingle()`) et `logger.start()` vivaient TOUS DEUX hors du try — une exception à l'une ou l'autre étape (`logger.start()` peut réellement rejeter sur un aléa réseau, même si les erreurs `{error}` qu'il reçoit de Supabase sont déjà avalées en interne) aurait fait sortir de la boucle `for` entière et coupé le traitement de toutes les orgs suivantes, pas seulement celle en échec — exactement l'inverse de la garantie annoncée. Corrigé : tout le corps par-org vit désormais dans le try (`stripe-webhook/index.ts`). Preuve : `supabase/tests/stripe-webhook-e2e.test.ts` invoque le vrai handler HTTP (`handleStripeWebhook`, nouvellement exporté) avec un client Supabase mocké dont l'insert `data_syncs` échoue spécifiquement pour org-a — vérifié vide (`git checkout main -- ...` temporaire) que ce test échoue bien contre le code d'avant ce correctif avant d'être validé contre le code corrigé, pour confirmer qu'il est réellement discriminant.
- 2026-08-20 (même vérification) — **Confirmé par écrit, aucun trou** : `data_syncs.webhook_event_id` n'a jamais porté de contrainte `UNIQUE` en base (vérifié dans `supabase/migrations/` — colonne déclarée `TEXT NULL` sans contrainte associée — et confirmé en direct sur le projet dev via `pg_constraint`/`pg_indexes` : seuls une PK sur `id`, deux FK et des index non-uniques existent sur cette table). L'« idempotence » de ce chemin est donc une décision applicative (lecture puis skip conditionnel), jamais un rejet DB — deux orgs légitimes partageant un event Stripe ne peuvent donc pas se bloquer mutuellement en écriture au niveau de la contrainte, quel que soit le scoping de la requête de lecture. C'est pour ça que le rescoping par `organization_id` (point ci-dessus) n'a nécessité aucune migration : rien à modifier au niveau contrainte, seulement le filtre de la requête `SELECT` qui décide du skip.

n'est pas un backlog priorisé — c'est un endroit où poser ce qu'on a vu sans

Les blocs `[functions.*]` du même fichier sont, eux, bien consommés par `functions deploy` (c'est ce qui porte `verify_jwt`).

## Cron jobs — jamais versionnés (2026-08-15, trouvé par le premier drift-check)

- 2026-08-15 — **Les 11 cron jobs du projet n'ont été créés par aucune migration.** `20260517000002_setup_cron_jobs.sql` ne contient pas un seul `cron.schedule` ; les jobs existent uniquement parce qu'ils ont été créés à la main sur ce projet. Corrigé par une garde (jobid + jobname), sans changer le comportement là où les jobs existent. Mais la garde ne fait que rendre le rejeu possible — elle ne recrée pas les jobs.

## Drift-check — job schéma connu rouge (2026-08-15)

- 2026-08-15 — Le job « Schéma base vs migrations » est **rouge en connaissance de cause**, et le restera tant que deux choses distinctes n'auront pas été traitées.
